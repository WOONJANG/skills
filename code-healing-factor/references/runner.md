# Evidence runner

Use Python 3.11 or later. On Windows, use a verified interpreter from Get-Command python or run py -3. On Linux and macOS, use python3. Paths with spaces or Unicode go in separate quoted arguments. The examples below use python.

1. Run `python -B <skill>/scripts/heal.py discover --root <project>`. Inspect nested instructions, manifests, CI, and `git status --short` separately. Discovery only reports root markers and available tools.
2. Copy [plan.example.json](plan.example.json) to a private task directory and adapt its checks. Freeze the plan before running baseline and final checks. Use a separate baseline state directory. Include source, fixtures, tests, relevant configuration and lockfiles in source. Directories are traversed recursively. Exclude only generated or irrelevant paths. Include every relevant worktree edit, including untracked inputs. Avoid a whole-repo scan when dependencies or build outputs are present.
3. Run `python -B <skill>/scripts/heal.py fingerprint --root <project> --plan <plan>`. Fill an assessment JSON object with project (the canonical absolute path from discover), fingerprint, gates and optional issues. Each gate value has status (PASS, FAIL, BLOCKED or NOT_APPLICABLE) and a nonempty reason with the evidence or rationale. Attach review PASS only after inspecting actual evidence. G04–G09 and G11 accept PASS only from executed checks.
4. Run `python -B <skill>/scripts/heal.py run --root <project> --plan <plan> --state <task-dir> --assessment <assessment>`. State must be outside the project. Leave G14 unset in the first run. It can yield BLOCKED even when every executable check passes. Inspect the report and the traceability evidence, record G14 against the same fingerprint if acceptance is established, and copy the report's run_id into the assessment. Invoke the same command with finalize instead of run. Finalize reuses the reviewed execution records and requires the same plan and source fingerprint. If the plan or source changed, run fresh checks. Refresh assessments after edits. When a runner check fails, rerun the same argv directly in the stated cwd to inspect sanitized diagnostics.
5. Before a repair, consult repair_policy in the current report and history.json. After the attempt, run the same command with `attempt` instead of `run` and add `--entry <attempt.json>`. An entry has issue, strategy, evidence (nonempty strings) and progress (boolean). Progress requires an observed improvement or a confirmed diagnostic result. A pivot requires a different strategy. Attempt logging rejects excess iterations and identical failed attempts. The agent enforces the budget before editing.

Use explicitly reviewed command arrays. Commands inherit the environment and host permissions. Checks run with closed stdin. Use native executables or explicit interpreters, with {python} for the running Python interpreter. Raw output is discarded by default to avoid persisting secrets. Optional stdout_sha256 compares small deterministic stdout with an independently calculated SHA-256 over exact bytes. Keep secrets, personal data and private payloads out of arguments, IDs, review text and attempt records. Keep task data local and remove the dedicated directory when no longer needed. Use workers above one only for independent read-only checks or isolated fixtures. Time limits apply to direct commands. Checks that spawn descendants must supervise them.

Plan fields include schema_version, level, required, source, exclude, checks, limits, repair and security_threshold. The runner adds level minimums to required. Each check takes id, gate, argv and optional cwd, timeout and stdout_sha256. Use a project-relative cwd. Limits are timeout (default 60 seconds), total_seconds (600), workers (1) and stdout_bytes (1 MiB, for digest comparisons). An unavailable executable, timeout or exceeded output limit yields BLOCKED. Test-framework exits may require an explicit wrapper if they distinguish no tests collected or environmental errors. Use real assertions and guard against all tests being skipped.

Each issue has id, category, location, severity, evidence, blocking and resolved. Include sanitized root-cause and reproduction details in evidence. An unresolved blocking issue, an unresolved security issue meeting the severity threshold, or any failed gate yields FAILED. A missing, stale or unavailable mandatory gate yields BLOCKED. Mandatory gates must all be PASS. A gate with several commands passes only if all succeed and the review records no failure or blocker for that gate.

The version 1.0 report contains project, status, level, normalized plan, checked and final fingerprints, required gates, gate states, check records (argv, cwd, timestamps, exit, status and reason), assessment, issues, blocker IDs, repair attempts and policy. completed is true only for PASS. A minimal BLOCKED report replaces prior evidence when a run starts. A lock prevents simultaneous updates to one task directory. After interruption, clear a leftover lock only after confirming that no process is using the state. Check current fingerprints before relying on any stored report. The runner is local evidence bookkeeping and trusts the supplied plan, reviewer and commands.

Run exit codes are 0 PASS, 1 FAILED, 2 BLOCKED, 3 invalid or unusable inputs. Helper commands use 0 for successful operation. The supplied tests use generated, isolated fixtures and run with `python -B -m unittest discover -s <skill>/tests -v`.


For STANDARD and STRICT plans, add a requirements object mapping each significant behavioral requirement ID to one or more execution check IDs. The report lists the mapped check outcomes by requirement. Review assertion coverage, test collection and skipped tests separately. Existing plans without the mapping remain valid.
